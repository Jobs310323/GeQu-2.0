# Промт для сессии Claude Sonnet 5 (High): Sechenov Student

> Этот файл — готовый текст для вставки в новую сессию. Отдавай его целиком.
> Инструкция по снятию исходных данных — в соседнем `CAPTURE_GUIDE.md`;
> без выполненного слепка портала промт запускать бессмысленно.

---

## §0. Роль, рамки и жёсткие запреты

Ты строишь **Sechenov Student** — персональный академический клиент поверх
официального студенческого портала Сеченовского Университета
(`https://student.sechenov.ru/`).

Портал остаётся единственным источником истины. Приложение **только читает** данные,
ничего не изменяет на портале и не пытается его заменить. Первая фаза — один
пользователь, но архитектура должна масштабироваться на многих без переписывания.

### Что запрещено — это не пожелания, это условия задачи

1. **Не начинай с frontend.** Пока нет рабочего парсера, доказанного тестами на реальных
   фикстурах, ни одной React-страницы не пишется.
2. **Не выдумывай API портала.** Любой URL, метод, параметр, имя поля, заголовок — только
   если он есть в HAR-файлах. Каждое утверждение в документации сопровождай ссылкой на
   конкретную запись HAR (файл + индекс запроса + URL).
3. **Не предполагай**, что расписание берётся одним запросом. Не предполагай, что хватит
   одного GET. Не предполагай наличие JSON API. Это выясняется из HAR, а не из опыта с
   другими сайтами.
4. **Никаких секретов в git.** Ни пароля, ни куки, ни сырого HAR. `fixtures/raw/` —
   в `.gitignore` первым коммитом.
5. **Не закрывай справочники в enum**, если портал может выдать новое значение (типы
   занятий, формы контроля, статусы). Свободная строка + известные значения отдельным
   справочником.
6. **Не выдумывай данные при парсинге.** Не распарсилось — сохрани raw, оставь поле
   `null`, запиши parser warning. Пустое честное поле лучше правдоподобного вранья:
   человек пойдёт не в тот корпус.
7. **Если фикстур не хватает — не гадай.** Пиши конкретный запрос в
   `docs/MISSING_CAPTURE.md` («нужен HAR перехода на месяц вперёд в расписании, чтобы
   понять формат параметра даты»), продолжай остальную работу и скажи об этом
   пользователю в конце хода. Не блокируйся целиком из-за одного пробела.
8. **Портал — чужой продакшн.** Между запросами не меньше 1 секунды, разумные таймауты,
   экспоненциальный backoff на ошибках, никаких параллельных веерных запросов.

## §1. Что у тебя на входе

- `fixtures/raw/*.har` — сетевые логи разделов портала, снятые пользователем в браузере
  под своей учётной записью (с телами ответов).
- `fixtures/raw/html/*.server.html` — HTML как его отдал сервер (`view-source:`).
- `fixtures/raw/html/*.dom.html` — DOM после выполнения JavaScript.
- `fixtures/raw/curl/*.txt` — точные запросы в формате `curl` с полным набором заголовков.
- `fixtures/raw/NOTES.md` — что снять не удалось и почему.

Чего у тебя **нет** и не будет:

- доступа к порталу из этой среды (egress-прокси режет всё, кроме github/npm/pypi);
- учётной записи студента;
- возможности «просто сходить и посмотреть».

Всё исследование — офлайн, по фикстурам. Это ограничение, но оно же даёт
детерминированность: парсер, написанный по зафиксированному HTML, тестируется без сети.

## §2. Стек

Новый отдельный репозиторий. Технологический профиль такой же, как в соседнем проекте
пользователя (GeQu-2.0), чтобы не плодить зоопарк:

- **Frontend:** Vite + React 19 + TypeScript (strict, без единого `any`) + Tailwind.
- **Backend:** Vercel serverless functions (`api/*.ts`, `@vercel/node`).
- **БД:** Neon Postgres (`@neondatabase/serverless`).
- **HTTP-клиент:** `undici` с ручным cookie-jar (`tough-cookie`) — не голый `fetch`,
  нужен контроль редиректов и куки.
- **Парсинг HTML:** `cheerio`.
- **Тесты:** `vitest`.
- **Линт:** `oxlint`.
- **Playwright:** только если §3 докажет, что без него данные недостижимы.

Скрипты в `package.json`: `dev`, `build`, `typecheck`, `test`, `lint`, `sync` (ручной
запуск синхронизации), `sanitize` (санитайзер фикстур).

## §3. Фаза 1 — Discovery. Файл `docs/REVERSE_ENGINEERING.md`

Это главный артефакт. Всё остальное — следствие.

### 3.1. Инструменты разбора

Напиши в `scripts/har.ts` небольшой разборщик HAR: список запросов с методом, URL,
статусом, content-type, размером, наличием тела. Дальше работай через него, а не
глазами по 40-мегабайтному JSON.

### 3.2. Санитайзер — до всего остального

`scripts/sanitize.ts`: читает `fixtures/raw/`, пишет `fixtures/sanitized/`.
Вырезает и заменяет плейсхолдерами:

- заголовки `Cookie`, `Set-Cookie`, `Authorization`, `X-CSRF-*` и любые `*token*`;
- тело POST-запроса авторизации целиком (но **имена полей сохраняет** — они и есть
  предмет исследования);
- ФИО, номер студбилета, e-mail, телефон, ID пользователя в URL и телах.

Только санитизированные фикстуры коммитятся и используются в тестах.

### 3.3. Что разобрать по каждому разделу

Разделы: **авторизация**, **моё расписание**, **промежуточная аттестация** (и каждая её
внутренняя вкладка: результаты, мастер-классы, практические навыки, консультации),
**ЭОР**, **дисциплины по выбору**, **образовательные проекты**, **оценка занятий**,
**профиль**, **выход**.

Для каждого — таблица строго в этом формате:

```
SOURCE            — человекочитаемое имя раздела
URL               — точный путь с параметрами, шаблон вида /schedule?date={YYYY-MM-DD}
HTTP METHOD       — GET / POST
AUTH REQUIREMENT  — какие куки/заголовки обязательны, что будет без них
DATA FORMAT       — server HTML / HTML-фрагмент по AJAX / JSON / смешанно
PARSER STRATEGY   — cheerio по селектору X / JSON-путь Y / требуется браузер
EVIDENCE          — файл HAR + индекс запроса, доказывающий всё вышеперечисленное
```

### 3.4. Авторизация — разобрать до конца

Отдельный раздел документа. Ответить на всё:

- URL страницы с формой; метод и `action` формы.
- Полный список полей формы, включая **hidden**: имена, значения, откуда берутся значения
  (константа / генерируется сервером / из cookie).
- Есть ли CSRF-токен, где он лежит (hidden-поле, meta-тег, заголовок, cookie) и меняется
  ли он между запросами.
- Точный POST: URL, `Content-Type` (form-urlencoded или multipart), набор полей.
- Цепочка редиректов после успешного логина: коды, `Location`, порядок.
- Все `Set-Cookie`: имена, флаги `HttpOnly`/`Secure`/`SameSite`, `Path`, `Expires`/`Max-Age`.
- Какие куки обязательны для последующих запросов, а какие можно не тащить.
- Как выглядит **неуспешный** логин, если это видно в фикстурах.
- Как выглядит запрос **с протухшей сессией** (блок E слепка): 302 на форму? 401?
  200 с формой в теле? — это определяет условие переавторизации в клиенте.
- Что делает logout и надо ли его вообще звать (для фонового синка — скорее нет,
  переиспользуемая сессия дешевле).
- Есть ли капча, MFA, привязка к User-Agent или IP.

### 3.5. Расписание — разобрать навигацию по датам

Ключевой вопрос всего проекта: **можно ли запросить произвольную дату/неделю напрямую.**

- Как передаётся дата: query-параметр, POST-поле, часть пути, AJAX-запрос?
- Точный формат даты (`YYYY-MM-DD`, `DD.MM.YYYY`, unix, номер недели?).
- Запрашивается неделя целиком или день? Есть ли диапазон `from`/`to`?
- Отдаётся ли при переключении недели **полная страница** или **HTML-фрагмент**/JSON?
- Есть ли ограничение по глубине (нельзя запросить прошлый семестр)?
- Как определяется текущий пользователь: из cookie-сессии, или в URL есть его id
  (это важно для будущей многопользовательности).

### 3.6. Структура одного занятия

Разбери HTML одной пары до последнего узла. В реальном интерфейсе информация о занятии —
длинный полуструктурированный текст. Задокументируй:

- какой DOM-контейнер соответствует одному занятию;
- какие поля лежат в отдельных узлах, а какие слиты в одну строку;
- есть ли `data-*` атрибуты, `id`, ссылки на детальную страницу;
- как выглядит разделитель между логическими частями (запятая, точка, `<br>`, `|`);
- какие бывают маркеры/бейджи типа события и дополнительных уведомлений;
- как выглядит день без занятий и как выглядит отменённое/перенесённое занятие,
  если это есть в фикстурах.

Приведи в документе **дословный пример** одного занятия (после санитизации) и рядом —
разбор на поля. Это станет первым golden-тестом.

### 3.7. Аттестация

- URL каждой вкладки; вкладки — это разные URL или один URL с параметром/AJAX?
- Пагинация: есть ли, как параметризуется, сколько записей на странице.
- Фильтры (семестр, учебный год): как передаются.
- Структура таблицы: список колонок в том порядке, в каком они идут в HTML, с
  примерами значений.
- Какие ячейки бывают пустыми — это прямое обоснование `nullable` в схеме.
- Какие реально встречаются значения формы контроля и результата — собери полный
  перечень из фикстур, он пойдёт в справочник.

### 3.8. Прочие разделы

ЭОР, дисциплины по выбору, образовательные проекты, оценка занятий, профиль —
по той же таблице из §3.3. Если раздел пуст у этого студента, так и напиши: «в слепке
раздел пустой, структура неизвестна» — и вынеси в `docs/MISSING_CAPTURE.md`.

## §4. Фаза 2 — Выбор стратегии парсинга. `docs/adr/ADR-001-parser-strategy.md`

Решение принимается **по фактам из §3**, дерево простое:

| Что показал HAR | Что делаем |
|---|---|
| Данные есть в `*.server.html` | `undici` + `cheerio`. Playwright не ставим. |
| Данные приходят XHR'ом в JSON | Бьём в этот endpoint напрямую, парсим JSON. |
| Данные приходят XHR'ом HTML-фрагментом | Бьём в endpoint, парсим фрагмент `cheerio`. |
| Данных нет в `*.server.html`, но есть в `*.dom.html` | Проверь ещё раз: они точно не приходят отдельным XHR? Браузер — последнее средство. |
| Иначе | Playwright, и только для тех разделов, где он необходим (hybrid). |

Сравни `*.server.html` и `*.dom.html` **программно** (скриптом, по наличию ключевых строк
вроде названия дисциплины и времени пары), а не на глаз. Приведи результат сравнения
в ADR как доказательство.

Правило: **минимально сложное устойчивое решение**. Playwright — это браузер в
serverless, холодный старт, память, лимиты Vercel и постоянные поломки. Тащим его,
только если доказано, что иначе никак.

## §5. Фаза 3 — Доменная модель и схема БД

**Схема описывает предметную область, а не DOM портала.** Если в HTML одна ячейка
содержит «кафедра, адрес, корпус, этаж, кабинет» — в БД это пять полей и две сущности,
а не одна строка.

### 5.1. Сущности

`users`, `portal_sessions`, `education_programs`, `academic_years`, `semesters`,
`subjects`, `teachers`, `departments`, `locations`, `schedule_events`, `assessments`,
`assessment_results`, `academic_events`, `sync_runs`, `change_events`, `notifications`,
`user_preferences`.

Общие правила:

- Обязательны только реально обязательные поля. Всё, что портал может не отдать —
  `nullable`. Пустое поле — валидное состояние, а не ошибка.
- У каждой синхронизируемой сущности: `source_url`, `source_id` (если портал его даёт),
  `source_hash`, `created_at`, `updated_at`, `first_seen_sync_id`, `last_seen_sync_id`.
- `source_hash` — стабильный хеш нормализованного содержимого записи. Считается по
  явно перечисленному набору полей, а не по `JSON.stringify` объекта (иначе порядок
  ключей и добавление поля ломают всю историю изменений).
- Естественные ключи для upsert выведи из данных, а не из порядка строк в HTML.
  Для занятия это, скорее всего, `(user_id, date, start_time, subject, group)` —
  но подтверди по фикстурам.

### 5.2. `schedule_events`

```
id, user_id, education_program_id, subject_id, teacher_id, department_id, location_id,
date, start_time, end_time, lesson_type, address, building, floor, room,
group_name, subgroup, raw_title, raw_description, parser_warnings,
source_url, source_id, source_hash, created_at, updated_at
```

- `date` — тип `date`. `start_time` / `end_time` — тип `time`.
  **Не UTC-инстанты.** Портал живёт в Europe/Moscow и мыслит календарём; хранение
  «пары в 8:30» как момента времени порождает сдвиги и вопросы, которых нет в источнике.
  Конвертация в момент времени — задача слоя представления, там же и таймзона.
- `lesson_type` — свободная строка. Известные значения — в справочнике, не в enum.
- `raw_title` / `raw_description` — исходный текст **всегда**, даже если распарсилось
  идеально. Это страховка на случай, когда портал поменяет формат, а мы заметим не сразу.
- `parser_warnings` — `jsonb`, список того, что не удалось разобрать в этой записи.

### 5.3. `locations`

Отдельная сущность (не строка в занятии), потому что цель — кнопка **«Открыть на карте»**:

```
id, university, address, building, floor, room, raw, lat, lng, created_at, updated_at
```

`lat`/`lng` — nullable, заполняются позже (геокодирование не входит в первую фазу,
но место под него в схеме должно быть). Дедупликация по нормализованному
`(address, building, floor, room)`.

### 5.4. `assessments`

```
id, user_id, education_program_id, semester, academic_year, discipline, practice,
control_form, result, assessment_date, exam_date, location_id, department_id,
assessment_kind, raw_row, parser_warnings,
source_url, source_hash, created_at, updated_at
```

- **Все поля nullable**, кроме `id`, `user_id` и источниковых.
- `assessment_kind` — свободная строка: зачёт, экзамен, промежуточная аттестация,
  практические навыки, консультация, мастер-класс, ЭОР, дисциплина по выбору,
  образовательный проект **и любое новое значение, которое реально встретится**.
  Неизвестное значение сохраняется как есть и порождает parser warning, а не исключение.
- Не проектируй модель как `Student → Marks`. Это разнородные учебные события с общей
  формой: «что», «когда», «где», «какой контроль», «какой результат».

### 5.5. `sync_runs`, `change_events`

```
sync_runs:    id, user_id, started_at, finished_at, status, sections jsonb,
              fetched_count, parsed_count, changed_count, warnings jsonb, error text

change_events: id, user_id, entity_type, entity_id, change_type, field_diffs jsonb,
               detected_at, sync_run_id, seen_at
```

`change_type` — `added` / `changed` / `removed`. `field_diffs` — список
`{field, before, after}`. Именно отсюда живёт экран «Изменения расписания», ради
которого всё и затевалось: студенту важно не текущее расписание, а то, что в нём
поменялось со вчера.

### 5.6. Миграции

Обычные пронумерованные SQL-файлы в `migrations/`, применяются идемпотентным раннером
(`scripts/migrate.ts`). Никакого ORM с автогенерацией схемы — схема здесь важнее удобства.

## §6. Фаза 4 — Парсеры и golden-тесты

### 6.1. Форма парсера

Каждый парсер — чистая функция: `(html: string) => ParseResult<T>`, где

```ts
type ParseResult<T> = {
  items: T[];
  warnings: ParserWarning[];   // { scope, field, message, raw }
};
```

Никаких запросов к сети внутри парсера. Никаких исключений на неожиданных данных:
неизвестное — это warning, а не падение. Парсер, который роняет весь синк из-за одной
странной пары, хуже парсера, который вернул её наполовину пустой.

### 6.2. Нормализация текста занятия

Разбор полуструктурированной строки — по правилам, выведенным из фикстур, а не по
универсальной регулярке «на все случаи». Порядок:

1. Разбить по документированным разделителям.
2. Определить каждый фрагмент по маркерам («каф.», «корп.», «этаж», «ауд.», индексы,
   шаблон ФИО и т.д.).
3. Всё уверенно распознанное — в нормализованные поля.
4. Всё остальное — в `raw_description`, поле `null`, warning с исходным фрагментом.

Правило разрешения сомнений: **лучше `null`, чем догадка.** Ошибочный кабинет хуже
отсутствующего кабинета — по отсутствующему человек откроет портал, по ошибочному
придёт не туда.

### 6.3. Тесты

- Для каждого парсера — санитизированный входной HTML в `fixtures/sanitized/` и
  ожидаемый JSON рядом. Snapshot-тесты `vitest`.
- Обязательные кейсы: полный день; пустой день; занятие с отсутствующей аудиторией;
  занятие с неизвестным типом; таблица аттестации с пустыми `result` и `exam_date`;
  строка с неизвестной формой контроля.
- Тест «неизвестное значение не роняет парсер и порождает ровно один warning».
- Тест дедупликации `locations`: два занятия в одной аудитории → одна запись.
- Тест стабильности `source_hash`: одинаковый вход → одинаковый хеш; изменение
  незначащего пробела → тот же хеш; изменение аудитории → другой хеш.

Фаза не закрыта, пока все парсеры не проходят тесты на реальных фикстурах.

## §7. Фаза 5 — Клиент портала

`src/portal/client.ts`:

- cookie-jar (`tough-cookie`), ручное управление редиректами (`redirect: 'manual'`)
  — цепочка редиректов после логина сама по себе несёт информацию.
- `login()` строго по §3.4: GET формы → извлечь hidden-поля и CSRF **из ответа**,
  не из константы → POST → сохранить куки.
- Определение протухшей сессии — по признаку, задокументированному в §3.4
  (редирект на форму / 401 / форма в теле). Одна автоматическая переавторизация,
  затем ошибка.
- Между запросами — пауза не меньше 1 с. Таймаут на запрос. Retry с экспоненциальным
  backoff (2s, 4s, 8s) **только на сетевых ошибках и 5xx**; 4xx не ретраится.
- `User-Agent` как у обычного браузера, `Accept-Language: ru-RU`.
- Логи запросов без куки и без тела логина.

### Учётные данные

Первая фаза — один пользователь: логин и пароль портала живут **в переменных окружения**
`SECHENOV_LOGIN` / `SECHENOV_PASSWORD` (Vercel Environment Variables), не в БД и не в
браузере. Это осознанный выбор: пока пользователь один, хранилище паролей — лишняя
поверхность атаки.

При переходе на многих пользователей: пароли шифруются AES-GCM ключом из окружения,
таблица `portal_credentials` отдельно от `users`, ключ ротируется. Напиши это в
`docs/adr/ADR-002-credentials.md` сразу, чтобы решение было принято осознанно, а не
случайно, когда появится второй пользователь.

## §8. Фаза 6 — Синхронизация и обнаружение изменений

`src/sync/run.ts`:

1. Логин (или переиспользование живой сессии).
2. Обход разделов в фиксированном порядке, с паузами.
3. Парсинг → нормализованные записи + warnings.
4. Upsert по естественному ключу.
5. Сравнение `source_hash` с сохранённым → `change_events`.
6. Записи, которых больше нет в источнике, **не удаляются**: помечаются
   `removed_at` и порождают `change_event` типа `removed`. Исчезнувшая пара — это
   отмена занятия, самая ценная новость в приложении, и терять её нельзя.
7. Запись `sync_runs` со статусом, счётчиками и warnings.

Расписание синкается на окно: текущая неделя ± 2 (уточни по §3.5, какая глубина вообще
доступна). Аттестация — целиком, она маленькая.

Триггеры: Vercel Cron (несколько раз в день; ночью реже) + ручной запуск из UI
с защитой от частых повторов.

Частичный отказ не роняет прогон: упал один раздел — остальные синкаются, статус
`partial`, ошибка в `sync_runs.error`.

## §9. Фаза 7 — API

Vercel functions в `api/`, все под авторизацией пользователя приложения (не портала):

```
GET  /api/schedule?from=YYYY-MM-DD&to=YYYY-MM-DD
GET  /api/schedule/next          — следующее занятие (или следующее учебное событие)
GET  /api/assessments?kind=&semester=&year=
GET  /api/changes?since=         — лента изменений
GET  /api/sync/status            — последний прогон
POST /api/sync                   — ручной запуск
GET  /api/preferences  /  PUT /api/preferences
```

Ответы — нормализованный домен, а не сырой HTML. Ошибки — единый формат
`{ error, detail }`. Никогда не отдавай наружу куки портала и любые его заголовки.

## §10. Фаза 8 — Frontend

### 10.1. Dashboard

Главный экран **не копирует таблицу портала**. Цель: за 2–3 секунды человек понимает,
куда ему идти. Порядок блоков:

1. Текущая дата.
2. **Следующая пара** — самый крупный элемент экрана.
3. Countdown до неё.
4. Занятия на сегодня.
5. Ближайшие учебные события.
6. Ближайшие аттестации.
7. Недавние изменения.
8. Статус синхронизации.

### 10.2. `NextLessonCard` — отдельный компонент

Показывает: время начала и конца, название дисциплины, тип занятия, преподавателя,
аудиторию, корпус, этаж, адрес, countdown.

Состояния — все три обязательны:

- **идёт сейчас** — показать текущую пару и сколько до конца;
- **сегодня ещё будет** — показать ближайшую и сколько до начала;
- **сегодня пар больше нет** — показать следующее учебное событие с указанием дня
  («завтра», «в понедельник»), а не пустоту.

Плюс: кнопка «Открыть на карте» (когда есть адрес) и «Открыть на портале».

### 10.3. Расписание

- **Today** — вертикальный timeline с «сейчас»-маркером.
- **Week** — календарная сетка/timeline, переключение недель, свайп на мобильном.
- **Day** — полная временная шкала дня.

Карточка занятия: дисциплина, время, длительность, тип, преподаватель, кафедра,
аудитория, корпус, адрес.

Требования к вёрстке, они не косметические:

- длинные названия дисциплин переносятся (`overflow-wrap: anywhere`), не обрезаются
  многоточием — «Безопасность жизнедеятельно…» бесполезно;
- **никакого горизонтального overflow страницы**; широкое содержимое скроллится внутри
  своего контейнера;
- на 360px ширины всё читаемо.

### 10.4. Аттестация

Отдельный раздел «Аттестация». Вместо огромной таблицы — группы и карточки:

```
Промежуточная аттестация

04.12.2026
Безопасность жизнедеятельности
Зачёт
Результат: —

18.11.2026
Биоэтика
Зачёт
Результат: —
```

Группировка по типу события, сортировка по дате, отсутствующее значение — «—», а не
пустое место и не выдуманный ноль. Фильтры по семестру/году, если портал их даёт.

### 10.5. Изменения

Лента `change_events` человеческим языком: «Пара перенесена: Биоэтика, 12.11, было
14:00 ауд. 305 → стало 16:00 ауд. 412». Непрочитанные — отдельно.

## §11. Фаза 9 — PWA и уведомления

- `vite-plugin-pwa`, офлайн-доступ к последнему синхронизированному расписанию
  (расписание нужно ровно там, где нет сети — в корпусе).

## §12. Фазы и критерии приёмки

| Фаза | Готово, когда |
|---|---|
| 0. Скаффолд | Репозиторий, стек, `.gitignore` с `fixtures/raw/`, `typecheck`/`lint`/`test` зелёные на пустом проекте |
| 1. Discovery | `docs/REVERSE_ENGINEERING.md` покрывает все разделы, каждое утверждение с EVIDENCE; пробелы вынесены в `docs/MISSING_CAPTURE.md` |
| 2. Стратегия | `ADR-001` с программным сравнением server-HTML и DOM |
| 3. Схема | Миграции применяются на чистой БД и идемпотентны; `ADR-002` про креды |
| 4. Парсеры | Все парсеры зелёные на санитизированных фикстурах, включая кейсы из §6.3 |
| 5. Клиент | `npm run sync -- --dry-run` логинится и достаёт разделы (проверяет пользователь локально) |
| 6. Синк | Полный прогон пишет в БД, повторный прогон даёт 0 изменений, подмена одной записи даёт ровно один `change_event` |
| 7. API | Все endpoint'ы отвечают, неавторизованный запрос — 401 |
| 8. UI | Dashboard и расписание работают на реальных данных, нет горизонтального overflow на 360px |
| 9. PWA | Устанавливается, работает офлайн, пуш доходит |
| 10. Hardening | Ошибки портала не роняют UI, есть пустые состояния, есть экран «синхронизация не удалась» |

Фазы идут по порядку. Не начинай следующую, пока предыдущая не закрыта по критерию.

## §13. Гигиена работы

- Перед каждым коммитом: `npm run typecheck && npm run lint && npm run test`. Всё зелёное.
- Коммиты по фазам, с осмысленным сообщением о том, **что и почему**, а не «fix».
- TypeScript strict. `any` — нет. `unknown` + сужение — да.
- Комментарии объясняют причину решения, а не пересказывают код.
- Секреты — только в переменных окружения. `.env.example` без значений.
- В конце каждой фазы — короткий отчёт пользователю: что сделано, что выяснилось про
  портал, чего не хватает для следующего шага.
