# ADR-006 — Internationalization

**Status:** accepted (Phase 11)

## Context

GeQu was built as a monolingual Russian product. Measured before starting:
**2278 lines containing Cyrillic across 136 files**, `index.html` fixed at
`lang="ru"`, Clerk hardcoded to `ruRU`, 41 `toLocale*` call sites (two of them
pinned to `'ru-RU'`), and `₽` written out at 13 places in `Finance.tsx` —
appended *outside* the `fmt()` helper, so currency was not centralised either.

Two things in that count are not UI strings and must not be treated as such:

- **Long-form editorial content** (`lib/knowledge.ts`, `lib/cbt.ts`, ~310 lines
  of Markdown articles). A forty-line article inside a JSON string value is
  unreadable in a diff and unusable by a translator.
- **Validated instrument wording** (`lib/clinicalTests.ts`, 290 lines). See
  below.

## Decision

### Library: `react-i18next`, with `Intl` doing every format

i18next handles the fallback chain, missing-key behaviour, namespace loading,
plural *category selection* and `<Trans>` for embedded markup — the places a
hand-rolled `t()` quietly goes wrong. Russian needs three plural forms
(one/few/many), and the boundaries are not intuitive: 11–14 are `many` while 21
is `one`.

But i18next only *selects*. Formatting goes through `src/lib/format.ts`, which
is `Intl.DateTimeFormat` / `NumberFormat` / `RelativeTimeFormat` / `PluralRules`
/ `Collator` directly. A library's own date layer is one more thing to be subtly
wrong about Russian genitive months, and the platform is already right.

`src/lib/datetime.ts` is untouched. It decides *which day a record belongs to*
in the user's timezone and formats nothing; `format.ts` formats and decides
nothing. Merging them would blur the one distinction `datetime.ts` exists to
enforce.

### Resources are bundled, not fetched

Two locales of UI strings are tens of kilobytes. A network round-trip before
first paint, in an app whose point is opening fast, is a bad trade. Long-form
content is the exception and is loaded per article.

### Keys are written out, not derived

`nav.ts` carries `labelKey: 'nav:items.kanban.label'` rather than deriving the
key from `id`. It duplicates the id twenty times and buys two things: grepping
for a key finds its call site, and `check:i18n` verifies each key exists without
knowing anything about `nav.ts`.

### Insights carry keys and parameters, never prose

`Insight` gained `messageKey`, `params` (literals, including the user's own tag
text) and `paramKeys` (values that are themselves keys). A detector that
returned a finished sentence could only be tested by matching that sentence, and
could only ever speak one language.

`params` and `paramKeys` are separate fields rather than i18next's inline
`$t()` nesting because nesting inside an interpolated value only expands with
`interpolation.skipOnVariables: false` — and that switch applies to every
interpolated value, including the user's own tag. A tag named `$t(...)` would
then be evaluated against the translation table. Two fields cost a line; the
alternative is an injection point.

### Currency is a user setting, not a locale derivation

A Russian speaker in Berlin spends euros; an English speaker in Moscow spends
roubles. `prefs.currency` defaults to `RUB` — not a guess from the browser,
because every amount already stored was entered as roubles and displayed with a
hardcoded `₽`. Relabelling those numbers as dollars would misstate the user's
own data.

### Existing users stay in Russian

Locale resolution is: stored choice → **`ru` if this browser already holds
`gequ_*` data** → `navigator.languages` → `en`.

The middle step is the one that looks odd and is the one that matters. Every
existing user is Russian-speaking, and the app had no language setting until
now, so none of them can have expressed a preference. Falling through to
`navigator.language` would open their app in English one morning with the way
back written in English. That is data continuity, not taste, and
`src/i18n/locale.test.ts` asserts it.

## Instruments are not translated

`lib/clinicalTests.ts` holds ASRS-v1.1 Part A, PHQ-9, PSS-10 and WHO-5 with
their real per-item scoring. The Phase-0 audit flagged this file as *a thing to
protect*.

**The wording is the instrument.** Round-tripping PHQ-9 items through a
translation produces something that looks like PHQ-9 and scores like PHQ-9 and
is not PHQ-9. So:

- English is the source language for all four in reality; the Russian here is a
  translation of it. The `en` locale carries **published English item wording**,
  entered as content — never generated from the Russian.
- Russian strings stay byte-identical. Nothing is re-derived.
- An instrument whose validated wording cannot be stated accurately for a locale
  is **hidden in that locale** with a visible note, never shown
  machine-translated.
- Instrument text lives in `src/lib/instruments/{en,ru}.ts` — data files outside
  the translation-key system, so no tooling can helpfully auto-fill them.
  `clinicalTests.ts` keeps the scoring, which is locale-independent.

Landed in 11b: `lib/instruments/{ru,en}.ts` holds the per-locale wording,
`lib/clinicalTests.ts` the locale-independent scoring, merged by array
position per instrument id. English wording was checked against
authoritative sources rather than translated from the Russian; see
`docs/GEQU_PROGRESS.md`'s Phase 11b entry for which two instruments (CFQ,
MDQ) could not be fully independently verified item-by-item in this
environment and should get a follow-up review.

## Consequences

- Adding a locale means adding a directory under `src/i18n/locales/`, an entry
  in `SUPPORTED_LOCALES`, and a Clerk bundle. No code changes for plurals.
- `check:i18n` fails the build on key drift, so partial migration is safe.
- The bundle grew by ~20 kB gzipped for i18next plus both locales.
- A locale with a different plural system than Russian's needs no code change:
  `Intl.PluralRules` supplies the categories and the gate checks them per
  locale.
